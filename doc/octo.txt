INTRODUCTION                                    *octo*

Edit and review GitHub issues, pull requests, and discussions from the comfort
of your favorite editor.

Use `gO` to access the contents of this helpfile.


USAGE                                           *octo-usage*

Edit the issue title, body, or comments, as a regular buffer and use `:w(rite)`
to sync the issue with GitHub.


HEALTH CHECK                                    *octo-health*

Run `:checkhealth octo` to verify your installation. The report covers:

- `octo.nvim`      setup() was called
- `Neovim version` minimum and recommended version requirements
- `Dependencies`   gh CLI binary, plenary.nvim, picker plugin, file panel icon provider
- `Authentication` active GitHub account, token source, and token scopes

If any check fails, follow the advice shown in the report.


LUA API                                         *octo-lua-api*

The plugin exposes a Lua API to iteract with GitHub CLI which powers the
plugin.

The `octo.gh` module is meant to mirror the GitHub CLI as closely as possible.
For example, >lua

    local gh = require "octo.gh"

    gh.issue.list {}
<

This is equivalent to running `gh issue list` in the terminal.

Any CLI arguments can be passed as well. For example, >lua

    local gh = require "octo.gh"

    gh.issue.list { label = "bug", limit = 5, state = "closed" }
<

This is same as `gh issue list --label "bug" --limit 5 --state "closed"` in
the terminal. Note: For parameters with `-`, use an `_` in the key instead.  For
example, `--add-assignee` becomes `add_assignee` in the Lua API.

Consult the GitHub CLI documentation for the available commands and
parameters at <https://cli.github.com/manual/> or use the `--help` flag.

By default, nothing is returned since the commands are asynchronous. Pass a
callback function to `cb` in the `opts` keyword: >lua

    local gh = require "octo.gh"

    gh.issue.list {
        opts = {
            cb = function(stdout, stderr, exit_code)
                vim.notify(stdout)
                vim.notify(stderr)
                vim.notify(exit_code)
            end,
        }
    }
<

Handle the output as needed directly use the `gh.create_callback` helper to
handle success and failure cases: >lua

    local gh = require "octo.gh"

    gh.issue.list {
        opts = {
            cb = gh.create_callback {
                success = function(stdout)
                    vim.notify("Success: " .. stdout)
                end,
                failure = function(stderr)
                    vim.notify("Error: " .. stderr)
                end,
            }
        }
    }
<

Use the defaults of `gh.create_callback` to notify the user on the stdout and
stderr automatically: >lua

    local gh = require "octo.gh"

    gh.issue.list {
        opts = {
            cb = gh.create_callback {},
        }
    }
<

The `mode` can be passed as well in order to access the output synchronous:
>lua
    local gh = require "octo.gh"

    local stdout, stderr, exit_code = gh.issue.list { opts = { mode = "sync" } }
<

Similarly, the REST and GraphQL endpoints can be used as well: >lua

    local gh = require "octo.gh"

    gh.api { "/notifications" }
<
This is equivalent to running `gh api /notifications` in the terminal.

Common REST actions are exposed for convenience: >lua

    local gh = require "octo.gh"

    -- Get
    gh.api.get(opts)

    ---Post
    gh.api.post(opts)

    --- Patch
    gh.api.patch(opts)

    --- Delete
    gh.api.delete(opts)
<

The GraphQL endpoint is also available. For example,
>lua
    local gh = require "octo.gh"

    gh.api.graphql {
        f = { query = "query { viewer { login } }" },
        jq = ".data.viewer.login",
    }
<
This is the same as >terminal

    gh api graphql -f query='query { viewer { login } }' --jq '.data.viewer.login'
<
in the terminal. Note: Single character keys are passed with single `-` in
the CLI.

Parameterized queries are also possible mirroring the syntax in CLI. Just pass
lua objects directly:
>lua
    local gh = require "octo.gh"

    gh.api.graphql {
        f = {
            query = [[
            query($owner: String!, $name: String!) {
                repository(owner: $owner, name: $name) {
                    issues(first: 1) {
                        totalCount
                    }
                    pullRequests(first: 1) {
                        totalCount
                    }
                    discussions(first: 1) {
                        totalCount
                    }
                }
            }
            ]]
        },
        F = { owner = "pwntester", name = "octo.nvim" },
    }
<

There are plenty of examples in the repo so consider checking it out for more
reference or read more in the GitHub discussion:
`Octo discussion edit 876 pwntester/octo.nvim`

COMMANDS                                        *octo-commands*

There is only one main command: `Octo <object> <action> [args]` command. If no
command is passed, the argument to `Octo` is treated as URL from where an
issue or PR number and repo are extracted.

Mappings for many of the commands can be easily configured - see |octo-config|.

See |octo-command-examples| for examples.


:Octo issue [action] {args}                     *octo-commands-issue*

  close                 Close the current issue.
  reopen                Reopen the current issue.
  create {repo}         Creates a new issue in the current or specified repo.
  edit [number] {repo}  Edits issue/PR with the given number in the current or
                        specified repo.
  list [repo] {key=val} Lists all issues satisfying a given filter.
                        In-menu mappings:
                          <CR>    Edit issue.
                          <C-b>   Open issue in browser.
                          <C-y>   Copy URL to system clipboard.
                          <C-e>   Copy commit SHA to system clipboard (where applicable).
                        Available filter keys: see <https://docs.github.com/en/graphql/reference/input-objects#issuefilters>

  reload                Reload issue. Same as doing `e!`.
  browser               Open current issue in the browser.
  url                   Copies the URL of the currently opened issue to the
                        system clipboard.
  subscription          Change subscription state (subscribe, unsubscribe, or ignore).
  pin                   Pin the current issue to the top of the list.
  unpin                 Unpin the current issue from the top of the list.

:Octo poll [action]                             *octo-commands-poll*

  start                  Start polling tracked buffers for remote changes.
  stop                   Stop polling.
  toggle                 Toggle polling on/off.
  status                 Show polling status and tracked buffers.
  apply                  Force-reload a dirty buffer with pending remote changes.

  Polling periodically checks GitHub for updates to open issue/PR buffers
  using a lightweight GraphQL query (only fetches `updatedAt`). When a
  remote change is detected:
  - If the buffer has no local edits, it is automatically reloaded.
  - If the buffer has unsaved local edits, the reload is skipped and
    the user is notified. Use `:Octo poll apply` to force-reload.

  Configure polling via the `poll` config table:
    `enabled`             (boolean, default false) Auto-start on buffer open
    `interval`            (number, default 10000) Polling interval in ms
    `notify_on_refresh`   (boolean, default true) Notify on auto-refresh
    `notify_on_change`    (boolean, default true) Notify when dirty skip

>

  Octo issue create
  Octo issue create pwntester/octo.nvim
  Octo comment add
  Octo reaction add hooray
  Octo issue edit pwntester/octo.nvim 1
  Octo issue edit 1
  Octo issue list createdBy=pwntester
  Octo issue list neovim/neovim labels=bug,help\ wanted states=OPEN
  Octo search assignee:pwntester is:pr
<

You can pass GitHub URLs directly to the Octo command, including GitHub
Enterprise URLs:
>
  " GitHub.com URLs
  Octo https://github.com/pwntester/octo.nvim/issues/12
  Octo https://github.com/pwntester/octo.nvim/pull/123

  " GitHub Enterprise URLs (hostname is automatically detected)
  Octo https://ghe.example.com/owner/repo/issues/456
  Octo https://ghe.example.com/owner/repo/pull/789
<

You can also use `octo://` URLs to open issues and PRs directly:
>
  " Open from the default GitHub instance (github.com or configured github_hostname)
  :e octo://owner/repo/issue/123
  :e octo://owner/repo/pull/456

  " Open from a specific GitHub Enterprise instance
  :e octo://ghe.example.com/owner/repo/issue/123
  :e octo://ghe.example.com/owner/repo/pull/456

  " Both singular and plural forms are supported
  :e octo://owner/repo/issues/123
  :e octo://owner/repo/pulls/456
<

The `octo://` URL format is especially useful for:
- Opening issues/PRs from notes or wiki links without needing to be in the
  repository directory
- Working with multiple GitHub instances (e.g., GitHub.com and GitHub
  Enterprise) without setting `GH_HOST` globally
- Creating quick links in your workflow that work regardless of your current
  directory

PR REVIEW                                       *octo-pr-review*

 Open the PR (eg: `Octo <PR url>` or `Octo pr list` or `Octo pr edit <PR number>`)
* Start a review with `Octo review start` or resume a pending review with `Octo review resume`
 A new tab will show a panel with changed files and two windows showing the diff on any of them.
 Change panel entries with `]q` and `[q` or by selecting an entry in the window.
* Navigate to unviewed files with `]u` (next unviewed) and `[u` (previous unviewed).
* Add comments with `<localleader>ca` or suggestions with `<localleader>sa` on single or
  multiple visual-selected lines
  * A new buffer will appear in the alternate diff window. Cursor will be
    positioned in the new buffer
  * When ready, save the buffer to commit changes to GitHub
  * Move back to the diff window and move the cursor, the thread buffer will
    hide
* Hold the cursor on a line with a comment to show a thread buffer with all
  the thread comments
  * To modify, delete, react or reply to a comment, move to the window
    containing the thread buffer
  * Perform any operations as if you were in a regular issue buffer
* Review pending comments with `Octo review comments`
  * Use <CR> to jump to the selected pending comment
* If you want to review a specific commit, use `Octo review commit` to pick a commit.
  * The file panel will get filtered to show only files changed by that commit.
  * Any comments placed on these files will be applied at that specific commit level and will be
    added to the pending review.
* When ready, submit the review with `Octo review submit`
* A new float window will pop up. Enter the top level review comment and exit
  to normal mode. Then press <C-m> to submit a comment, <C-a> to approve
  it or <C-r> to request changes


COMPLETION                                      *octo-completion*

Octo provides a built-in omnifunc completion for issues, PRs and users that you can trigger using `<C-x><C-o>`. Alternately, if you use [`nvim-cmp`](https://github.com/hrsh7th/nvim-cmp) or [`blink.cmp`](https://github.com/Saghen/blink.cmp) for completion, you can use the [`cmp-git`](https://github.com/petertriho/cmp-git/) or [`blink-cmp-git`](https://github.com/Kaiser-Yang/blink-cmp-git) source to provide issues, PRs, commits and users completion.

Also,you can use [`cmp-emoji`](https://github.com/hrsh7th/cmp-emoji) or [`blink-emoji.nvim`](https://github.com/moyiz/blink-emoji.nvim) to get markdown emoji completion.

ISSUE LAYOUT                                    *octo-issue-layout*

  With `ui.layout = "columns"` an issue buffer is laid out in two columns: the
  description on the left, its metadata in a sidebar on the right. The
  default, `"classic"`, renders the buffer exactly as it always has. >

    #101 Add a thing                              Feature  Completed  bug
    ────────────────────────────────────────────────────────────────────────
    User Story                                    │ PEOPLE
    As a user, I want the thing so I can do the   │ author    someone
    task without paging through empty weeks.      │ assignee  another
                                                  │ watching  all activity
    Problem                                       │
    The thing is missing...                       │ DATES
                                                  │ opened  Feb 18
    ┌ Acceptance criteria 1/3 ──────────────────  │ edited  8 days ago
    │ [ ] First row appears                       │ closed  6 hours ago
    │ [x] Second row appears                      │
    │ [ ] Third row appears                       │ LINKS
    └                                             │ parent  #90 Add more things
                                                  │ prs     #201 #202
                                                  │         all 2 merged
                                                  │
                                                  │ ACTIVITY  27 · newest first
                                                  │ 6h   closed as completed
                                                  │ 3d   parent issue added
                                                  │ 7d   2 PRs merged
                                                  │ Jul  board churn ×9,
                                                  │      assignee churn ×5
<
  Everything the layout adds is virtual text and extmarks. The title and the
  description are the real, editable text they always were, and `:w` sends
  them to GitHub byte for byte: nothing is padded, wrapped or rewritten to
  make the columns.

  Header~

  The number sits before the title and the chips after it, right-aligned:
  the issue type when the repository uses issue types, the state with its
  reason (`Completed`, `Not Planned`, `Duplicate`), the labels in their
  GitHub colours, and the status on each project board the issue is on.
  A rule runs under the title.

  Description~

  Markdown headings in the description (`#`, `##`, `###`) read as section
  titles: the hashes are concealed at `ui.conceallevel` 2 and the text takes
  `OctoLayoutHeading`. Concealed is not removed -- move the cursor onto the
  line and the markup is there, and it saves back unchanged.

  A run of task-list items (`- [ ]`, `- [x]`, at any indent) is drawn as a
  panel: a rail down its left, `OctoLayoutPanel` behind it, and a title above
  it reading `<title> <done>/<total>`. The title is the heading right above
  the run, or `Checklist` when there is none. Fenced code is left alone, and
  so is anything the parser cannot read: it then renders as it does in the
  classic layout rather than wrongly. Ticking a box from the panel is not
  wired yet -- edit the `[ ]` in the text and save, as before.

  Sidebar~

  The sidebar is grouped: PEOPLE (author, assignees, subscription), DATES
  (opened, edited, closed or updated -- relative while recent, a short date
  once not), LINKS (the parent issue, the pull requests that close the issue
  with how they stand, what blocks it and what it blocks, the milestone) and
  ACTIVITY (the timeline, newest first, a run of one kind of event collapsed
  into a count such as `board churn ×9`, bucketed by age, at most eight rows
  with the total in the group title).

  It is drawn beside the description, one row per line. A description line
  wide enough to reach the gutter keeps its space: the text always wins, and
  that row moves down to the next line with room. The sidebar is laid out
  again as you type, so it keeps yielding. When the description has fewer
  lines with room than the sidebar has rows, the first groups go in the block
  between the header and the description -- whole groups, so no heading is
  parted from its rows -- and whatever still finds no line hangs under the
  description as virtual lines. Narrower than
  `ui.min_main_width` there is no room for two columns and the whole sidebar
  hangs under the description instead.

  `<localleader>gl` (`goto_link`) on a LINKS row opens what it points at;
  where a row carries several, they are offered to choose from
  (|octo-links|).

  Options~

  `ui.layout`          `"classic"` (default) or `"columns"`
  `ui.sidebar_width`   width of the sidebar, 34 by default
  `ui.min_main_width`  narrower than this the sidebar hangs below, 56 by default

  Highlight groups~

  `OctoLayoutRail`      the rail between the columns and down a panel   `WinSeparator`
  `OctoLayoutRule`      the rule under the header                       `WinSeparator`
  `OctoLayoutGroup`     a sidebar group title                           `Comment`
  `OctoLayoutKey`       a sidebar row's key                             `Comment`
  `OctoLayoutHeading`   a heading in the description, a panel's title   `Function`
  `OctoLayoutPanel`     the background of a task-list panel             `CursorLine`


CI CHECKS                                       *octo-checks*

  A pull request buffer lists the CI checks of its head commit in the details
  section, grouped by outcome -- failures first, then running, skipped and
  passed checks, each with how long it took.

  The list is folded away behind its summary line, so the counts stay on
  screen while the rows do not: >

      Checks: 1 failed · 1 skipped · 12 passed  ▸ 14 checks

<  Toggle it with `<localleader>tc` (`toggle_checks`) from anywhere in the
  buffer, or with the usual fold keys (`za`, `zo`, `zc`) while the cursor is on
  it. The fold stays as you left it when the buffer reloads. Set
  `ui.fold_checks = false` to render the list unfolded and create no fold.

  With the cursor on a check, `<localleader>gc` (`goto_check`) opens it: the
  workflow run in an octo buffer for a GitHub Actions job, the check's target
  URL in the browser for anything else. When the line stands for several
  checks -- a workflow row in the columns layout, see |octo-layout| -- they
  are offered to choose from.


LAYOUT                                          *octo-layout*

  A pull request buffer lists its details as `Label: value` lines. With
  `ui.layout = "columns"` the same details are laid out in two columns
  instead: a main column with what the PR is, and a sidebar with what is
  happening to it: >

      #123 Add a thing to the widget page                OPEN  20 min review
      ─────────────────────────────────────────────────────────────────────
      CONTEXT                                  │ REVIEW
      repo        owner/repo                   │ ✓ approved · someone ✓
      author      someone (member)             │ ! merge: out-of-date with base
      opened      23h ago · upd 3m             │
      assignee    someone                      │ CHECKS  15 ✓ 1 ● 2 ⊘
      milestone   —                            │ ● CI / docker_build running
      subscribed  all activity                 │ ✓ CodeQL ruby 2m42s · js-ts 1m29s
                                               │ ✓ linters 7 jobs, slowest erb 1m8s
      BRANCHES                                 │ ⊘ Review App deploy, destroy
      from    feat-child                       │
      into    feat-parent                      │ DEPLOYMENTS  1 active
      tracks  #101 Move the thing              │ review  Active   1111bbb · 1h
                                               │
      DIFF                                     │ STACK  3 of 3 → master
      11 files    +255 -23  ■■■■□  4 commits   │ ▶ #123 Add a thing to the w…  READY
                                               │ │ #122 Remove the old entry…  READY
                                               │ └ #121 Support the new colu…  READY
      ─────────────────────────────────────────────────────────────────────
      <the body>
<
  The title line puts the number before the title; the state and the labels
  go to its right edge as chips. The layout is virtual text over empty
  lines: the title, the body and the comments are the same editable text as
  in the classic layout and still round-trip to GitHub on `:w`. The
  deployments (see |octo-links|) get a group of their own when there are
  any, one row per environment with the commit it holds and its age, and
  `<localleader>gl` on a row opens the environment.

  The sidebar is `ui.sidebar_width` columns wide (34). When the window leaves
  the main column narrower than `ui.min_main_width` (56) the sidebar goes
  below the main column instead. The block is laid out again as the window
  is resized, within the lines it took at render: a window narrowed since
  keeps the columns side by side rather than stacking into the body.

  The CI checks are compressed to a row per workflow: the glyph is the worst
  outcome among its jobs, followed by the jobs with their durations when they
  fit the sidebar, or by how many there were and the one worth knowing about
  -- a failing or running job, else the slowest -- when they do not. Past six
  workflows the rest fold into a `+N more` row. There is no fold here, since
  a fold hides whole buffer lines and those carry the main column too:
  `<localleader>tc` (`toggle_checks`) lifts the cap by rendering the buffer
  again from what GitHub last sent, and puts it back the same way, so it
  refuses while the buffer holds unsaved edits. `<localleader>gc`
  (`goto_check`) on a workflow row, or on the `+N more` row, offers the
  checks it stands for; `<localleader>gl` (`goto_link`) on a `tracks` row
  opens the issue it names, see |octo-links|.

  Issue buffers keep the classic list in either layout. >lua

      require("octo").setup {
        ui = {
          layout = "columns",
          sidebar_width = 34,
          min_main_width = 56,
        },
      }
<

FOLLOWING LINKS                                 *octo-links*

  `<localleader>gl` (`goto_link`) opens whatever the cursor is on, in this
  order:

    1. an issue or pull request reference written in the text, exactly as
       `goto_issue` reads it: the cursor is on it, so `Fixes #12, also #34`
       opens whichever of the two the cursor sits on. Numbers resolve to
       either kind, so a pull request number opens as a pull request buffer
    2. any other link written in the text, in a browser -- a markdown link or
       a bare URL
    3. the line's own links, for the lines whose text is virtual

  Three kinds of line carry links of their own:

    - the `Development:` line of a pull request, listing the issues the pull
      request closes
    - the `Deployments:` line of a pull request (see |octo-deployments|)
    - a timeline event that linked or mentioned an issue or a pull request, or
      deployed the branch

  Both are drawn as virtual text on an empty line, so there is no column for
  the cursor to sit on and no way to tell two references on one line apart --
  when a line carries several, they are offered to choose from instead, named
  by repository when that is not this buffer's own.


DEPLOYMENTS                                     *octo-deployments*

  A pull request buffer lists the deployments of its recent commits in the
  details section, the same source the pull request page reads: how many there
  are and what state they are in, then a line per environment with its state,
  the commit it put there, when, and who by: >

      Deployments: 1 in progress
           review  In Progress   fcfe729 · 2 minutes ago by someone

<  Every state shows, not only the ones that landed: queued, in progress,
  failed, and retired environments read as they are.

  An environment deployed again supersedes the deployment before it, whatever
  state either is in, so each environment appears once showing where it stands
  now; the attempts themselves stay in the timeline.

  Recent commits rather than only the newest one: a push has no deployment of
  its own until the workflow makes one, and reading only the head commit would
  show nothing over exactly the minutes there is something to watch. A
  deployment of a commit that has since been rebased away belongs to no
  pull request any more, and does not show -- the pull request page agrees.

  `<localleader>gl` (`goto_link`) on a line opens that deployment: the
  environment it put the code on, or the log of the attempt when there is no
  environment yet -- a deployment still in progress, or one that failed. On the
  summary line, where every environment is on offer, they are offered to choose
  from. The timeline's own "deployed to" events follow the same way.

  Deployments are read from GitHub proper. GitHub Enterprise Server is left
  alone, as it is for the other fields its older schemas may not carry.

FAQ                                             *octo-faq*

How can I disable bubbles for XYZ?~

  Each text-object that makes use of a bubble (except labels) do use their own
  highlight group that links per default to the main bubble highlight group.
  To disable most bubbles at once you can simply link `OctoBubble` to
  `Normal`. To only disable them for a certain plain do the same for the
  specific sub-group (e.g. `OctoUser`).

Why do my issue titles or markdown syntax do not get highlighted properly?~

  The title, body and comments of an issue or PR are special as they get
  special highlighting applied and is an editable section. Due to the latter
  property it gets the `OctoEditable` highlighting via a special signs
  `linehl` setting. This takes precedence over the buffer internal highlights.
  To only get the background highlighted by the editable section, set
  `OctoEditable` to a highlight with a background color definition only.

Why am I getting authentication error from gh?~

  This means that are either using a GITHUB_TOKEN to authenticate or `gh` is
  not authenticated.

  In case of the former, run:
>bash
  GITHUB_TOKEN= gh auth login
<
  ...and choose a method to authorise access for `gh`.
  `gh` must store the creds so it can work in a subshell.

  Run `:checkhealth octo` for a full diagnosis.

Can I use treesitter markdown parser with octo buffers?~

  Just add the following lines to your TreeSitter config:
>lua
  vim.treesitter.language.register('markdown', 'octo')
<

*How can I filter PRs by filter keys that aren't available?~

  You can use the search command `:Octo search [query]`.
  The [search syntax](https://docs.github.com/en/search-github/getting-started-with-searching-on-github/understanding-the-search-syntax) and available search terms are available in [GitHub documentation](https://docs.github.com/en/search-github/searching-on-github/searching-issues-and-pull-requests#search-by-author).

  For example to search for PRs with author you can use this command:

>vim
  :Octo search is:pr author:pwntester repo:github/codeql
<

  Note: You need to provide the `repo`, otherwise it will search for every PR by that user.

*How to enable autocompletion for issues/prs (`#`) and users (`@`)?~

  Add the following mappings for `octo` file type:

>lua
  vim.keymap.set("i", "@", "@<C-x><C-o>", { silent = true, buffer = true })
  vim.keymap.set("i", "#", "#<C-x><C-o>", { silent = true, buffer = true })


I can't see my v2 projects in issues and/or pull requests!~

  (and I see a warning when I open them)

  You are missing a scope from the token gh uses. You can add the scope to
  your gh token with

  `gh auth refresh -s read:project`

  Alternatively if you want to be able to modify projects (i.e. add/remove
  cards) you need to add the `project` scope to your token instead.

  If you don't care about projects v2 you can suppress the warning by setting
  `suppress_missing_scope.projects_v2 = true` in your Octo config.

  Run `:checkhealth octo` for a full diagnosis.

How can I disable default key mappings?~
  set `mappings_disable_default = true` in user config.
